# Controller load and recovery results — 2026-07-26

## Conclusion

The single-controller architecture is suitable for a production pilot when the
deployment stays within a tested work-cell size.

The tested starting points are:

- OpenHands Enterprise with an external V1 controller: two to four active
  conversations, queue excess work, and place no more than six trusted
  conversations in one grouped sandbox on the tested installation;
- OpenHands Enterprise with an in-platform prompt automation: two active child
  conversations in the tested cell; the four-active cell was rejected;
- Agent Canvas: one controller replica beside one trusted shared backend;
- native subagents: two to four specialists inside one top-level work cell,
  while the durable campaign controller remains outside the parent.

This is not evidence that one controller process should launch a hundred agents
at once. A large campaign should remain in a durable queue and admit bounded
cells as capacity becomes available.

The in-platform Enterprise pilot already proved Git checkpointing, restart
reattachment, unique conversations, shared-sandbox placement, and automation
cleanup across four attempts. The new six-task load proved the updated V1
client and bounded controller behavior, but its controller ran outside
Replicated. A combined high-concurrency automation run has not yet been
accepted.

The first combined four-worker automation test
(`62067818-eb39-4031-9dad-f6086c126199`) ran for 442.1 seconds. It created four
V1 conversations in one sandbox and the automation service cleaned up the

## Enterprise live load

All live runs used:

- OpenHands Enterprise 0.24.0 on Replicated;
- `FEWEST_CONVERSATIONS` placement;
- six first-class conversation records;
- four active workers with excess work queued;
- one shared sandbox;
- a global request pace of at least 0.75 seconds;
- Claude Haiku 4.5;
- deterministic validation outside each worker;
- a ten-sandbox installation limit and a launch lock at seven;
- verified sandbox pause after the batch drained.

### Failure discovery

Two matched six-task runs completed five valid tasks and one controller-level
failure each:

| Run | Valid | Wall time | Retries | Cleanup |
| --- | ---: | ---: | ---: | --- |
| Initial retry load | 5/6 | 744.8 s | 2 transport | paused |
| Descending-tail retry | 5/6 | 815.4 s | 0 | paused |

The same graph task failed in both runs. The conversation status was
`finished`, but the V1 event index returned 1,000 streaming events and no
durable final `MessageEvent`. The model work existed, but the controller could
not parse a contract from an empty final response.

The initial load harness also had its own retry wrapper around the new shared
client retry policy. That compounded worst-case delay. The harness now only
paces requests; one shared client owns bounded retries and exposes retry
counts.

### Compatibility policy

The final response path now:

1. prefers a durable agent `MessageEvent` or `FinishAction`;
2. reads the newest event tail when a chronological result is capped;
3. only after terminal state is known, reconstructs the agent response from
   ordered `StreamingDeltaEvent` chunks if no durable message exists;
4. sends the reconstructed response through the same strict contract parser
   and deterministic validator;
5. records `ControllerRecoveredStreamingText` in safe event-count metadata.

The controller never treats streaming text itself as proof of correctness.

## Agent Canvas controller

The local Agent Canvas service passed a two-tick controller test:

- the service was healthy and ready with zero active conversations;
- tick one created the run and recorded sequence 1;
- tick two was a separate controller process;
- tick two resumed the same run ID and recorded sequence 2;
- both first-class Canvas conversations produced valid candidates;
- the two attempts took 33.3 and 25.6 seconds.

The second attempt duplicated the first candidate. This is expected for a
one-task diagnostic and reinforces that durable state does not replace
scheduling policy.

This tick test complements the existing three-replicate GKE result. In that
experiment, one managed controller assigned six different tasks before launch.
It achieved six times the task coverage of six independent controllers, with
22.9% lower mean wall time and 23.8% lower mean model cost.

The two-tick controller ran as a local process against Canvas. The documented
Kubernetes CronJob placement uses the same API and state contract, but the
CronJob packaging itself was not separately load-tested.

## Native subagents

No new Enterprise subagent load was run because the tested Replicated profile
still did not advertise the task tool after the setting was enabled. Treat that
as an integration gap, not a failed performance benchmark.

The existing Agent Canvas test is sufficient to place native subagents:

- four parallel native children completed 4/4 strict visible contracts;
- parallel native delegation took 333.9 seconds;
- sequential native delegation took 501.4 seconds;
- four first-class Canvas conversations took 374.4 seconds and completed 3/4
  strict visible contracts in that replicate;
- a controlled bad child did not prevent three healthy siblings from
  completing.

Native children are therefore useful inside a trusted bounded work cell. They
are not independently assignable conversations and should not own the durable
campaign queue.

## What can be recommended

### Recommend now

- A single durable controller with deterministic validators and an immutable
  application-owned ledger.
- Enterprise first-class conversations for independently owned work.
- Two to four active trusted conversations per grouped Enterprise cell on the
  tested installation when the controller runs as an external service, with
  excess work queued.
- Two active child conversations per in-platform automation cell on the tested
  installation.
- Agent Canvas plus one controller for a trusted single-team shared backend.
- A hybrid in which top-level conversations may use two to four native
  subagents for bounded specialist work.
- Git checkpoints for release, audit, and restartable state when there is one
  controller.
- An external Enterprise controller service for sustained high-concurrency
  campaigns, or the tested two-child in-platform automation for bounded
  scheduled cells.

### Keep as an explicit boundary

- Use an application-owned database when multiple controllers claim work
  concurrently.
- Do not use OpenHands internal PostgreSQL tables.
- Do not share one runtime across tenants, untrusted code, or conflicting
  credentials.
- Do not recommend native subagents on the tested Replicated version until the
  task tool is advertised and the same tests pass.
- Do not increase the in-platform automation above two active children without
  repeating the load and contract checks. The four-active cell completed at
  the automation layer but produced only 3/4 independently verifiable
  contracts.
- Re-run load, failure, and cleanup tests after platform, SDK, image, model, or
  limit changes.
- A full NeuroGolf production run still needs the real ONNX workload,
  adversarial validators, artifact quarantine, and a submission gate.
