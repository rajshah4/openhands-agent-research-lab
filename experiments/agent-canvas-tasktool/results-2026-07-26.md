# Native Agent Canvas TaskToolSet test — 2026-07-26

## Outcome

Native TaskToolSet delegation worked in the local Agent Canvas stack.

The parent received the `task` tool, invoked one `code-explorer` subagent, and
received a matching `TaskObservation` with task ID `task_00000001`. In the
successful attempt, the child read a two-line test file and returned both the
expected first line and line count. The parent then emitted the required final
contract without reading the file itself.

This is evidence for native SDK subagents in Agent Canvas. It is not evidence
that the same setting currently works in the tested OpenHands
Enterprise/Replicated profile.

- Agent Server, SDK, tools and workspace packages: `1.36.1`
- Model: `openhands/claude-sonnet-4-6`
- Parallel tool calls: `1`
- Parent conversations: one at a time
- Native child type: `code-explorer`
- Kubernetes: not used; the previous GKE pilot had already been torn down
- Replicated sandboxes: not used

The Agent Server advertised `task_tool_set` and `task` before launch. The
conversation system prompt exposed the `task` tool alongside the ordinary
terminal, file editor and task-tracker tools.

### Concurrency behavior

In both native runs, the parent emitted all four `TaskAction` events within
milliseconds. With tool concurrency `1`, the observations returned serially
over 456.513 seconds. With tool concurrency `4`, the children overlapped and
the observations returned out of request order over 301.276 seconds.

Parallel native delegation therefore reduced:

- total parent wall time by 33.4% compared with sequential native delegation;
- total model cost by 15.2%; and
- wall time by 10.8% compared with four first-class conversations.

The speedup was about 1.5×, not 4×. All children still shared one Agent Server
process, one workspace and the same model-provider path. The slowest parallel
child took about 301 seconds, showing that higher logical concurrency does not
create four independent units of runtime capacity.

### Contract failures

The sequential store child performed the requested analysis and returned all
known symbols, but omitted its `case_id`; it passed deterministic content
coverage and failed the strict contract.

The first-class store conversation completed its internal analysis but exposed
only a short completion sentence as its final response. The required symbols
were not present in the durable final contract, so the controller correctly
counted it as invalid. Separate conversation status alone was not enough to
prove usable output.

These failures reinforce the need for controller-side contract validation
regardless of execution pattern.

## Architecture decision

The measured default for a trusted, read-only specialist group is one parent
with two to four native subagents. It had the lowest wall time, lowest measured
cost and one compact parent record in this replicate.

Use first-class conversations when independent ownership, visible histories,
per-agent retry, separate permissions or human handoff matter more than compact
execution. They share the Agent Canvas backend, so they improve logical
isolation and auditability but do not create compute isolation.

For large production campaigns, use a hybrid:

1. keep top-level work items in the external scheduler and experiment ledger;
2. assign each independently retryable work item to a first-class conversation
   or bounded Enterprise cell;
3. allow that work-cell owner to use two to four native subagents for trusted
   read-only exploration, test execution or synthesis; and
4. use isolated Enterprise sandboxes for untrusted code, conflicting writes,
   separate credentials or strong failure boundaries.

Do not place a hundred agents beneath one parent. That would concentrate
context, lifecycle, workspace and failure handling in one process and one
conversation. Scale by adding bounded work cells, then use subagents inside
each cell.

The bad child did not prevent its siblings from finishing, and the controller
identified only that child as invalid. This demonstrates useful sibling
containment for independent parallel tasks.

It does not make native children equivalent to first-class conversations. The
parent still owns their common lifecycle and final aggregation. A retry must be
issued through that parent/controller context, and a child does not have its
own UI record for an operator to assign, inspect or hand off. First-class
conversations create more operational objects, but those objects are
independent units of ownership, retry, permissions and service-level tracking.

## Decision criteria

Cost remains an observed metric, not the primary selection rule. Choose the
execution boundary in this order:

1. **Failure scope:** decide how much work may fail together.
2. **Ownership:** decide whether each worker needs an independently assignable
   history, retry and human handoff.
3. **Trust:** decide whether workers may share a filesystem, compute and
   credentials.
4. **Lifecycle:** decide who starts, drains, pauses, recycles and repairs the
   runtime.
5. **Capacity:** bound active work and queue the remainder.
6. **Cost:** compare the acceptable designs after the operational requirements
   are satisfied.

Enterprise is not required to orchestrate agents. An external scheduler,
durable experiment ledger, deterministic validator and Canvas or SDK workers
can form a production system for one trusted team that is prepared to own the
control plane.

Enterprise is valuable when the organization wants supported self-hosting,
first-class conversation records, access controls, sandbox lifecycle,
operator-visible state and grouped placement without rebuilding those
boundaries. More conversations are justified when they are useful operational
objects, not because every specialist inherently needs one.

## What this execution pattern means

The parent and child do not become two first-class Canvas conversation records.
TaskToolSet runs the child as a persisted SDK `LocalConversation` beneath the
parent, using the same Agent Server process and working directory. The child
gets its own task context and separately reported model-cost scope, while the
parent blocks until the child returns when parallel tool calls remain at `1`.

That makes the pattern useful for:

- bounded specialist work inside one trusted workspace;
- lower execution-management overhead than external conversation creation;
- parent-controlled delegation with explicit child cost accounting; and
- sequential research, code exploration or validation steps.

It does not provide the same runtime isolation, independent UI record, or
failure boundary as separate Enterprise conversations.
