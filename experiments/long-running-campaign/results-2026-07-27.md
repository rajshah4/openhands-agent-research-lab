## How the in-platform controller works

1. A prompt automation starts on the hourly trigger.
2. `supervise-endurance-tick.sh` starts exactly one background controller and
   records its PID, log, and atomic exit status in the automation sandbox.
3. `preset_tick.py` checks out the controller state branch and resumes the
   existing campaign.
4. The scheduler selects one task and launches or recovers one OpenHands worker.
5. The worker runs real tool-using research and pushes its compact result to a
   unique Git artifact branch.
6. The controller fetches the artifact, applies the deterministic validator,
   promotes only validated lessons, and checkpoints every transition to Git.
7. The automation service releases the grouped sandbox when the controller
   finishes because `keep_alive` is false.

The controller and worker were observed using the same sandbox ID. That grouped
placement is efficient, but it also means child cleanup cannot be handled as if
the worker were isolated. The automation service owns cleanup for the shared
sandbox. For isolated conversations, the controller instead pauses each child
sandbox explicitly.

## Live qualification sequence

The qualification deliberately kept failed canaries. They exposed limits that
short successful runs did not.

| Stage | Observation | Change |
| --- | --- | --- |
| Long event polling | Repeated full-history reads timed out on a long conversation. | Status polling now reads conversation state; event reads are bounded and reserved for terminal recovery. |
| Transient authentication | One run exhausted a burst of transient `BearerTokenError` responses. | The outer polling loop now continues after a bounded retry burst until the overall deadline. |
| Prompt-controlled dwell | An agent ignored an instruction to wait seven minutes. | The controller now enforces the lifecycle window independently of the agent. |
| Searchable event history | Two long workers reached the deployment's observed 1,000-event search boundary; their JSON responses were truncated. | Workers push result contracts to unique Git branches. Conversation events are diagnostic, not the sole result channel. |
| Shared-sandbox cleanup | The first automation treated the child as isolated and requested a pause on its own shared sandbox. | Grouped runs defer cleanup to the automation service; isolated runs retain explicit child pause. |
| Foreground terminal timeout | A long foreground controller command was retried, producing repeated recovery attachments. The controller did not launch a duplicate worker, but the retries were wasteful. | An idempotent background supervisor uses a PID file and status polling. |
| Recovery dwell | Recovery repeated a completed ten-minute dwell. | A prior cleanup request or completed dwell now satisfies the recovery dwell gate. |

## Durable state

The controller branch contains:

- immutable campaign manifest;
- scheduler decisions;
- start-task, conversation, sandbox, and automation identifiers;
- lifecycle checkpoints;
- artifact source and length;
- independent validation result;
- candidate hash and duplicate flag;
- promoted lessons;
- per-task best score;
- generated report; and
- controller progress.

Git is suitable here because there is one state-writing controller and the
history is useful evidence. A larger service with many concurrent controllers
would keep the same contracts and validator but move coordination, leases, and
high-frequency state to a transactional store.
