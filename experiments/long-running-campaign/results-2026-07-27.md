# Long-running Enterprise controller campaign

Date: 2026-07-27  
Deployment: OpenHands Enterprise on Replicated  
Campaign: `neurogolf-endurance-live`

## Result

The hourly OpenHands automation completed an eight-attempt campaign over nine
hours. Seven attempts produced independently valid candidates. One attempt
failed during controller recovery after its agent had already finished and
written a durable Git artifact.

This was a controller and deployment qualification using Kaggle-shaped
deterministic optimization tasks. It was not a full NeuroGolf ONNX training and
submission run.

## What each worker did

The endurance protocol required each agent to:

1. implement an exact or exhaustive baseline;
2. implement a standard greedy heuristic;
3. implement a seeded randomized or local-search refinement;
4. run at least 12 deterministic trials;
5. identify a case where the weakest approach made a worse choice;
6. verify every task constraint;
7. write the final contract to a unique Git artifact branch; and
8. return the same contract through the OpenHands conversation.

The controller, rather than the agent, applied the deterministic validator.
Successful first attempts for each task promoted a reusable lesson only after
validation.

It did not guarantee diverse exploration. Attempt 8 returned the same optimal

scheduler should pass prior candidate hashes and failed approach summaries,
then require a distinct method or explicitly stop work whose expected value is
low.

## How the in-platform controller worked

1. The hourly prompt automation started an OpenHands automation sandbox.
2. `supervise-endurance-tick.sh` started exactly one background controller and
   recorded its PID, log, and atomic exit status.
3. `preset_tick.py` checked out
   `experiment/endurance-controller-state` and resumed the existing campaign.
4. The scheduler selected one task and retrieved validated lessons from the Git
   ledger.
5. The controller started or recovered one OpenHands worker conversation.
6. The worker ran tool-using research and pushed its result to a unique Git
   branch.
7. The controller fetched that artifact, applied deterministic validation,
   promoted eligible lessons, and checkpointed every transition to Git.
8. The automation service released the grouped sandbox because
   `keep_alive` was false.

The controller and worker used one grouped sandbox. That placement reduced
runtime count, but the automation service—not the child worker—owned cleanup.

## Long-lifecycle evidence

- Every successful attempt included a controller-enforced 600-second lifecycle
  window. The controller did not rely on the agent to wait correctly.
- Attempt 1 survived several recovery attachments without creating another
  worker and ultimately recorded one validated attempt.
- Attempt 3 crossed an hourly boundary and took 70 minutes from selection to
  final record. The next automation tick recovered the same conversation and
  artifact.
- All durable campaign state survived across short-lived automation sandboxes.
- The final attempt completed normally in 619 seconds and used two lessons
  produced by earlier workers.

The agents generally completed their research and Git handoff in several
minutes. The longer lifecycle test therefore validates supervision, durable
handoff, recovery, and controller continuity. It does not claim that each
individual model call reasoned continuously for an hour.

## Missing-sandbox recovery finding

Attempt 7 exposed a production-relevant ordering problem:

1. The agent conversation reached `finished`.
2. Its 1,173-character Git artifact was available.
3. The controller retrieved the terminal response from Git.
4. The controller began the remaining portion of its 600-second dwell.
5. The next hourly automation tick reattached to the same start task.
6. The original sandbox was then `MISSING`.
7. Recovery failed before validating the already-durable artifact.

The failed agent used $0.198112695, 55,625 prompt tokens, and 4,372 completion
tokens. No duplicate conversation was created, and the failure remained in the
ledger.

The recovery path should treat a durable, parseable Git artifact plus a
terminal conversation checkpoint as sufficient input to validation. Sandbox
status should govern cleanup evidence, not invalidate a completed result. A
focused acceptance test is still required after changing that ordering.

## Other robustness changes established during qualification

| Finding | Implemented response |
| --- | --- |
| Repeated full-history reads timed out on long conversations. | Poll conversation status; reserve bounded event reads for terminal recovery. |
| Transient authentication failures exhausted one retry burst. | Continue bounded retry bursts until the overall deadline. |
| An agent ignored an instruction to wait. | Enforce dwell time in the controller. |
| Long event histories reached the deployment's observed search boundary. | Use Git artifacts as the durable result channel. |
| Grouped child cleanup attempted to pause its own automation sandbox. | Let the outer automation own grouped-sandbox cleanup. |
| Foreground controller retries caused repeated recovery attachments. | Use an idempotent background supervisor with PID and status files. |
| Recovery repeated a completed dwell. | Reuse a prior completed dwell or cleanup checkpoint. |

## Durable state

The controller branch contains:

- the immutable campaign manifest;
- scheduler decisions and retrieved lesson IDs;
- start-task, conversation, sandbox, and automation identifiers;
- append-only lifecycle checkpoints;
- Git artifact source and content length;
- independent validation results;
- candidate hashes and duplicate flags;
- promoted lessons;
- per-task best scores;
- the generated report; and
- controller completion status.

Git was sufficient because one controller owned the ledger. Multiple active
controllers would require transactional claims and leases behind the same
`ResearchStore` interface.

## Conclusion

The experiment validates that an OpenHands Enterprise automation can operate a
multi-hour, multi-conversation research campaign using Git as durable state.
It preserved task ownership, validated cross-conversation memory, recovered
work across automation ticks, retained failures, and released automation
sandboxes.

Two improvements remain before recommending this exact controller unchanged:

1. validate a durable terminal artifact before requiring the original sandbox
   during recovery; and
2. use prior candidates and approach history to avoid spending an attempt on a
   known duplicate.
