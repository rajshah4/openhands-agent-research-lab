# Agent Canvas on GKE pilot — 2026-07-25

## Outcome

The experiment demonstrated that one Kubernetes-hosted Agent Canvas backend can
run at least six OpenHands agent conversations concurrently without creating
one pod per conversation. All 13 measured attempts across concurrency 1, 2, 4,
and 6 completed successfully and passed the independent graph-coloring
validator.

This validates the shared-backend execution model for a trusted research team.
It does not add tenant isolation: the Canvas deployment remains a single-tenant,
shared-pod and shared-volume system.

Kubernetes was not the limiting resource in this test. Peak observed usage at
six concurrent conversations was 265m CPU and 707 MiB memory, with zero pod
restarts. The important limit was organizational: six independent agents
produced only two unique candidates.

## Deployment

- Platform: GKE Autopilot, `us-central1`
- Cluster: disposable `agent-canvas-pilot`
- Release and namespace: `agent-canvas-research`
- Workload: one StatefulSet pod and one 20 GiB persistent volume
- Access: private `ClusterIP` service through a localhost port-forward
- RBAC: disabled
- Pod requests: 500m CPU and 1 GiB memory
- Pod limits: 2 CPU and 4 GiB memory
- Cluster provisioning: 8 minutes
- Canvas cold workload startup: approximately 2 minutes 40 seconds on the first
  cluster and 3 minutes 18 seconds after recreation
- Pod restarts during all measured phases: 0

The localhost URL did not mean Canvas ran locally. The browser connected to a
localhost port-forward that carried traffic to the private service in GKE.

### Interpretation

- The shared Canvas pod handled six concurrent conversations with substantial
  CPU and memory headroom relative to its 500m/1 GiB requests.
- Throughput improved from concurrency 1 to 2, then degraded at 4 and 6 because
  several agents took much longer and consumed larger prompts.
- Validation yield remained 100%, so increased concurrency did not corrupt
  workspaces or the result contract.
- Unique-candidate yield fell from 100% at concurrency 1 and 2 to 50% at 4 and
  33% at 6. More unscheduled agents mostly repeated work.
- The result supports the core NeuroGolf hypothesis: infrastructure can make
  concurrency cheap, but an external scheduler and shared experiment ledger are
  needed to turn concurrency into useful research coverage.

## Sequential memory comparisons

Two matched comparisons tested cross-conversation validated memory. Each arm
used an isolated ledger, identical tasks, the same Canvas backend and model, and
the same attempt budget.

| Campaign | Tasks/arm | Naive quality | Managed quality | Naive lessons | Managed lessons | Naive cost | Managed cost |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Multi-family live pilot | 6 | 1.000 | 1.000 | 0 | 3 | $0.1095 | $0.1155 |
| Multi-family scale | 12 | 1.000 | 1.000 | 0 | 18 | $0.2298 | $0.2855 |
| Hard-transfer live | 6 | 1.000 | 1.000 | 0 | 3 | $0.2398 | $0.2702 |

Managed memory worked mechanically in every run, but did not improve model
quality because Haiku reached every known target without it. The additional
lesson context increased observed cost by 5% to 24%. This is evidence against
adding memory indiscriminately: retrieval needs a relevance and expected-value
gate.

The hard-transfer campaign first passed an offline control comparison, where
managed normalized quality improved from 0.814 to 0.847. Its live tie shows
that benchmark discrimination depends on the worker's baseline capability.

## Concurrent scheduling comparison

The strongest experiment held the Kubernetes backend, model, six-agent
concurrency, iteration limit, timeout, and campaign constant. Only task
assignment differed:

- Naive: six independent controllers each saw an empty ledger and selected
  their own first task.
- Managed: one external scheduler assigned the six campaign tasks without
  overlap before launch.

| Metric | Naive | Managed |
| --- | ---: | ---: |
| Agents | 6 | 6 |
| Independently valid | 6/6 | 6/6 |
| Tasks covered | 1/6 | 6/6 |
| Duplicate task assignments | 5 | 0 |
| Unique candidates | 1 | 6 |

| Observed model cost | $0.2801 | $0.1612 |
| Peak CPU | 335m | 301m |
| Peak memory | 788 MiB | 798 MiB |

External scheduling increased task coverage sixfold and reduced both wall time
and model cost by approximately 42%. This is direct evidence that the
organization layer matters even when the underlying agents and infrastructure
are unchanged.

## Matched deployment-model comparison

The next comparison held managed scheduling constant and changed the deployed
execution stack. Both arms ran the same six preassigned hard-transfer tasks,
six concurrent agents, Claude Haiku 4.5 model family, 600-second timeout,
worker contract, and deterministic validators. Each arm contributed three
successful replicates.

| Aggregate metric | Agent Canvas on GKE | Enterprise/Replicated |
| --- | ---: | ---: |
| Independently valid | 18/18 | 18/18 |
| Mean task coverage per batch | 6/6 | 6/6 |
| Mean batch wall time | 140.7 s | 270.5 s |
| Wall-time range | 104–171 s | 231.5–320.9 s |
| Effective throughput | 153.55 tasks/hour | 79.86 tasks/hour |
| Mean attempt latency | 101.1 s | 169.9 s |
| Mean reported model cost | $0.2008 | $0.2028 |
| Restarts | 0 | 0 |

Canvas had 48.0% lower mean batch wall time and 92.3% higher effective
throughput. Reported model cost was effectively tied. This is a comparison of
real deployment stacks, not only their worker containers: Canvas calls one
shared agent server directly, while Enterprise adds asynchronous
app-conversation creation, authentication, metadata, sandbox lifecycle, and
global control-plane limits.

An initial Replicated run discovered a `100 requests/minute` app-API limit after
all six conversations had reached the grouped sandbox. It was excluded from
the performance aggregate because five controllers lost terminal status. With
one shared request every 0.75 seconds, all three accepted Replicated runs
completed without a `429`, used one runtime each, and paused their sandboxes.

The practical conclusion is not that one deployment replaces the other.
Agent Canvas is the lighter and faster shared backend for one trusted team.
Replicated is the governed platform when identity, organizations, supported
lifecycle controls, UI-visible conversation records, or stronger isolation
options matter.

## Issues found

1. A controller-side `Path.resolve()` rewrote the Linux remote workspace path
   into a macOS `/System/Volumes/Data/...` path. Remote workspace paths now
   bypass controller-local path resolution.
2. An OpenHands API key was initially supplied to a direct OpenAI profile.
   Canvas stored it correctly, but the provider rejected it with HTTP 401. The
   successful run used the authorized Anthropic provider key.
3. The existing `.env` file is not safe to source as shell code. The pilot read
   only the named `ANTHROPIC_API_KEY` assignment as data.
4. A phase sampler must set `PYTHONPATH` explicitly when invoking the source
   checkout outside its virtual environment. The load harness now does so.

No credential values are stored in repository artifacts.

## Customer guidance

Use Kubernetes Agent Canvas when a trusted team wants a simple, efficient,
shared agent backend and accepts shared filesystem and process boundaries. It
is materially lighter than creating a separate Kubernetes workload for every
conversation.

Use OpenHands Enterprise/Replicated when customers need authentication,
multi-user governance, stronger runtime isolation, or untrusted workloads.
Canvas on Kubernetes is a useful execution option, not a replacement for those
Enterprise controls.

Proposal-level deduplication within one task remains a useful follow-on, but it
is no longer required for the deployment or Replicated operating guidance.
The matched Replicated pattern matrix has now completed separately.

The replacement `agent-canvas-pilot` cluster can be torn down after this
evidence is committed. Recreate it later if proposal-level deduplication becomes
a priority; keeping the idle cluster is no longer necessary for the completed
comparison.
