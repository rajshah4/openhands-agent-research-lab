# In-cluster Agent Canvas controller results

Date: 2026-07-27

This experiment placed the research controller inside the same GKE cluster as
Agent Canvas. It tested scheduled controller ticks, durable file-backed state,
restart recovery, and protection against overlapping controllers. It did not
use Codex or a laptop process to make scheduling decisions after each job was
started.

## Environment

| Component | Tested value |
| --- | --- |
| Cluster | GKE Autopilot `agent-canvas-pilot`, `us-central1` |
| Kubernetes server | `v1.35.6-gke.1127000` |
| Agent Canvas | `ghcr.io/openhands/agent-canvas:1.5.2` |
| Controller image | `us-central1-docker.pkg.dev/platform-team-sandbox-62793/agent-sandbox/openhands-agent-research-controller:e0b095f` |
| Controller image digest | `sha256:5b39f318d2be0fde2975acb58dc36a59a932f9797edfaa308c03be3e9c4e3c4c` |
| Model | `anthropic/claude-haiku-4-5-20251001` |
| Controller state | Dedicated `ReadWriteOnce` PVC |
| Worker state | Agent Canvas conversation store and workspace volume |
| Schedule during tests | Suspended; each tick was started manually |

The checked-in CronJob runs one attempt per tick, uses
`concurrencyPolicy: Forbid`, has no Kubernetes API credential, and reads the
Canvas API key from a Kubernetes Secret. `backoffLimit: 0` prevents Kubernetes
from silently retrying an ambiguous controller failure.

## Forced controller failure and recovery

A separate state directory was used so this test could not alter the completed
campaign.

1. The first controller created conversation
   `7938b09c-55a6-4df5-9ccf-a428f8187cdb`.
2. It persisted the `conversation_running` lifecycle record on the controller
   PVC.
3. Its pod was force-deleted with zero shutdown grace.
4. The worker conversation finished independently.
5. A replacement controller read the same run and attempt IDs, attached to the
   existing conversation, validated its terminal output, and recorded the
   attempt.

| Result | Measured value |
| --- | ---: |
| Run ID | `hard-transfer-live-20260727T131804Z-b95028e8` |
| Conversations before replacement | 7 total |
| Conversations after replacement | 7 total |
| Recovery lifecycle markers | 1 |
| Recovered attempts | 1 |
| Valid recovered attempts | 1 |
| Duplicate candidates | 0 |
| Recovered attempt elapsed time | 40.132 seconds |
| Recovered attempt model cost | $0.0351823 |

The final attempt record contains
`"recovered_after_controller_restart": true`. No replacement conversation was
created.

An earlier graceful-deletion diagnostic is not counted as crash evidence.
Kubernetes resumed the stopped process during its termination grace period, so
the original controller completed its write before exiting. The zero-grace test
above removed that ambiguity.

## Overlapping controller test

Two manual jobs, `agent-canvas-controller-overlap-a` and
`agent-canvas-controller-overlap-b`, were started against the same fresh state
directory. This deliberately bypassed the CronJob's normal overlap prevention.

- One job acquired the file-store ownership lock, created one conversation, and
  recorded one valid attempt.
- The other exited with code 2 and
  `another controller owns file store /state/overlap-live`.
- Only one worker conversation was created.

This verifies the single-controller design. The file lock rejects concurrent
ownership; it does not distribute claims across several controllers. A
transactional database or lease service is still required before running
multiple active controller replicas.

## What this establishes

The controller can run entirely beside Agent Canvas in Kubernetes. A scheduled
job plus durable state is enough for one controller to coordinate a campaign
across many short-lived controller processes. The controller can recover a
worker that outlives it, and duplicate prevention does not depend only on the
Kubernetes scheduler.

This test does not establish multi-controller horizontal scaling, tenant
isolation, or full NeuroGolf solution quality. Those require a transactional
claim store, production access controls, the real competition workloads, and
submission-specific validation.

## Operational state after the test

- The Agent Canvas StatefulSet is running with one ready replica and zero
  restarts.
- All eight observed test conversations are finished.
- The controller CronJob is still suspended.
- Its state path is restored to `/state/research-lab`.
- The GKE cluster remains running and was not deleted.

## Reproduction commands

Build the immutable controller image:

```bash
gcloud builds submit \
  --project PROJECT \
  --config experiments/agent-canvas-kubernetes/controller/cloudbuild.yaml \
  --substitutions \
  _IMAGE=REGION-docker.pkg.dev/PROJECT/REPOSITORY/research-controller:COMMIT \
  .
```

Create one bounded tick:

```bash
kubectl -n agent-canvas-research create job \
  --from=cronjob/agent-canvas-research-controller \
  agent-canvas-controller-canary

kubectl -n agent-canvas-research wait \
  --for=condition=complete \
  job/agent-canvas-controller-canary \
  --timeout=25m

kubectl -n agent-canvas-research logs \
  job/agent-canvas-controller-canary
```

Before enabling the recurring schedule, verify the attempt record, controller
status, Canvas conversation count, and pod restart count. The schedule can then
be enabled explicitly:

```bash
kubectl -n agent-canvas-research patch cronjob \
  agent-canvas-research-controller \
  --type=merge \
  -p '{"spec":{"suspend":false}}'
```

Do not enable more than one controller replica while using the file store.
