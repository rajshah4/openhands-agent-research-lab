# Replicated in-platform controller results — 2026-07-26

## Result

The Replicated installation can run the research controller inside OpenHands
without an external Codex process or a separate controller database.

The working pattern is:

1. a repository-backed OpenHands prompt automation;
2. one deterministic controller command per automation run;
3. a dedicated Git branch as the durable experiment ledger;
4. first-class V1 worker conversations;
5. controller and worker placement in one Enterprise sandbox; and
6. `keep_alive: false`, with the automation service owning final cleanup.

The four-attempt pilot reached `status: completed`. It created four unique
start tasks and four unique worker conversations. One worker conversation was
reattached during recovery, so the ledger contains five
`conversation_ready` events but no duplicate conversation.

## What the failure tests established

### Controller interruption and Git recovery

The first live worker reused the automation controller's sandbox. The original
worker cleanup code requested a pause for that sandbox, which interrupted the
controller before it finished recording validation.

The next controller process read the lifecycle ledger, found the stored
start-task ID, reattached to the same worker conversation, and completed the
attempt without launching a duplicate. This is direct evidence that the Git
ledger is sufficient for controller recovery.

The production rule from this test is simple: when the automation controller
and worker share a sandbox, the inner worker must not pause it. The outer
automation owns cleanup after the controller returns.

### Attempt-level failures

Two attempts were recorded as infrastructure failures:

- one recovered conversation's sandbox was missing after the deliberate
  controller cancellation;
- one conversation-status read returned a transient HTTP 401.

The controller recorded both failures immutably and continued the campaign.
That behavior is manageable, but not yet the production policy. A production
campaign should retry retryable infrastructure failures without consuming the
task's scientific attempt budget.

## Replicated compatibility findings

Four installation-specific details were required.

1. The lower-level custom-tarball automation had no user-bound secret store.
   Its agent-server session was valid, but `GITHUB_TOKEN` and
   `OPENHANDS_API_KEY` were unavailable.
2. The custom callback credential returned HTTP 401. The supported prompt
   preset's SDK workspace lifecycle handled callbacks correctly.
3. The automation service advertised SDK `1.33.0`, while the installed agent
   server emitted the `1.36` event contract. The experiment-local preset
   overlay pins `openhands-sdk`, `openhands-tools`, and `openhands-workspace`
   to `1.36.0`.
4. Enterprise repository preparation can be shallow or retain an older
   checkout. The controller now refreshes `origin/main`, unshallows the clone,
   checks out the Git state branch, and merges current controller code before
   resuming.

No OpenHands PostgreSQL table was read or modified for controller state.

## Reproducible operator path

The checked-in helpers preserve the commands used:

- `automation/register-preset.sh` registers the dormant user-bound automation;
- `automation/patch-preset-sdk.sh AUTOMATION_ID` applies the SDK compatibility
  package and refreshes the checked-in prompt;
- `automation/preset_tick.py` prepares the state branch and runs one tick;
- `run_tick.py --live --defer-sandbox-cleanup` runs the bounded controller
  reconciliation.

The shared client now has bounded, duplicate-safe transient retries. A
subsequent four-active/six-task Enterprise controller load completed 6/6 valid
tasks in one grouped sandbox with no retries or pause errors. The same test
also exposed and resolved a version-specific event-index condition in which a
finished conversation retained streaming chunks but no final `MessageEvent`.
See
[`experiments/controller-load/results-2026-07-26.md`](../controller-load/results-2026-07-26.md).

Keep the scheduled automation dormant until the updated main branch is
promoted into its pinned preset and one fresh automation tick is observed.
The current evidence establishes the controller logic, V1 load behavior,
in-platform serial recovery, shared-sandbox density, and cleanup. It does not
yet establish a long unattended operating window.
